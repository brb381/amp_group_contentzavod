# План проектирования архитектуры платформы

**Цель:** Спроектировать простую self-hosted архитектуру «Контент-завода AMP», которая будет развиваться после MVP без преждевременных распределённых систем и лишних зависимостей.

**Подход:** Начинаем с модульного монолита. Одно приложение FastAPI содержит бизнес-правила, PostgreSQL является единственным источником достоверных данных, React работает как статический клиент в браузере. Модули вызывают друг друга внутри приложения через явно определённые сервисы и транзакции, а не по HTTP. Отдельный Celery-воркер выполняет длительные, периодические и повторяемые операции через Redis, поэтому HTTP-запросы не выполняют интеграции или пакетную обработку напрямую.

**Технологии:** React + TypeScript + Vite только для сборки фронтенда, Python + FastAPI, PostgreSQL, Redis, Celery, Nginx, Docker Compose. RabbitMQ в первой версии не используется.

---

## Принципы архитектуры

1. Один модульный монолит, а не набор микросервисов.
2. PostgreSQL хранит все операционные, финансовые, согласительные и аудиторские данные и является единственным источником истины.
3. Каждое изменение данных выполняется в одной транзакции БД. Балансы и статусы выплат никогда не вычисляются по состоянию очереди задач.
4. Браузер не обращается напрямую к БД или внешним интеграциям.
5. Каждый внешний поставщик отделён небольшим адаптером. Детали YouTube, SMTP и будущих соцсетей не попадают в бизнес-правила.
6. Celery-воркеры выполняют длительную, периодическую и повторяемую работу. API только валидирует команды и фиксирует их результат в БД.
7. В первой версии не используются: общий event bus, service mesh, микросервисы, RabbitMQ, Kubernetes.

## Схема системы

```text
Браузер
  |
  | HTTPS, один домен
  v
Nginx
  |-- /              -> собранные статические файлы React
  |-- /api/v1/*      -> FastAPI
  |-- /health        -> FastAPI
  v
Модульный монолит FastAPI
  |-- учётные записи и доступ
  |-- профиль блогера и социальные аккаунты
  |-- каталог товаров
  |-- контент и модерация
  |-- просмотры и расчёты
  |-- выплаты
  |-- обращения, уведомления, аудит
  v
PostgreSQL

FastAPI / Celery Beat -> Redis (очередь задач) -> Celery Worker -> PostgreSQL и внешние сервисы
```

Node.js и Vite нужны только на компьютерах разработчиков и в CI для сборки React-приложения. На сервере Node.js постоянно не работает: Nginx раздаёт уже собранные статические файлы.

## Границы модулей

| Модуль | Чем владеет | Что может использовать |
| --- | --- | --- |
| Доступ | Пользователь, пароль, сессия, роль, статус аккаунта | аудит |
| Блогеры | Профиль, тип получателя, социальные аккаунты | доступ |
| Каталог | Бренд, товар, артикул, обязательные хештеги | доступ для проверки прав сотрудника |
| Контент | Карточка ролика, URL публикации, нормализация URL | блогеры, каталог, модерация |
| Модерация | Решения, причины, история проверки | контент, блогеры |
| Просмотры | Показания, принятые стартовые точки, результаты сбора | контент |
| Финансы | Расчётный период, начисление, баланс, запрос выплаты | просмотры, доступ |
| Обращения | Тикеты, сообщения, намерения отправить уведомление | доступ, блогеры |
| Аудит | Неизменяемый журнал значимых действий | все модули через один небольшой интерфейс |

Модуль может вызывать только явно определённый сервис другого модуля. Он не должен напрямую читать или изменять таблицы, которыми владеет другой модуль.

## Правила данных и взаимодействия

### Чтение

1. React обращается к версии API: `/api/v1/...`.
2. FastAPI проверяет сессию и роль пользователя.
3. Ответственный модуль читает PostgreSQL и возвращает валидированный DTO-ответ.
4. React отображает результат; расчёты и бизнес-правила на фронтенде не выполняются.

### Изменение данных

1. React отправляет команду в `/api/v1/...`.
2. FastAPI проверяет аутентификацию и права.
3. Модуль проверяет допустимость смены статуса и остальные бизнес-правила.
4. Одна транзакция PostgreSQL изменяет данные модуля и создаёт запись аудита.
5. Если требуется фоновая работа, та же транзакция записывает событие в outbox; задача Celery отправляется только после успешного сохранения данных.
6. API возвращает уже сохранённый результат команды.

### Пример: создание запроса выплаты

1. Финансовый модуль проверяет, что аккаунт блогера может запрашивать выплату.
2. В транзакции блокируется строка текущего баланса.
3. Создаётся один запрос на всю доступную подтверждённую сумму.
4. Сумма переносится из доступного в заблокированный баланс, пишется запись аудита.
5. Транзакция фиксируется. Уведомление менеджера создаётся как фоновая задача, но не влияет на создание запроса выплаты.

## Первая часть: проектирование веб-сервера

### Шаг 1. Граница HTTP API

**Будущие файлы:**
- `backend/app/main.py`
- `backend/app/api/router.py`
- `backend/app/api/v1/router.py`
- `backend/tests/api/test_health.py`

1. Добавить `GET /health` с минимальным статусом сервиса, без внутренних деталей БД.
2. Все рабочие маршруты вложить в `/api/v1`.
3. Ввести единый JSON-формат ошибок: `code`, `message`, необязательное поле `details`.
4. Написать тест маршрута здоровья.

### Шаг 2. Маршрутизация на сервере

**Будущие файлы:**
- `infra/nginx/default.conf`
- `infra/docker-compose.yml`

1. Nginx направляет `/api/` и `/health` в контейнер FastAPI.
2. Nginx раздаёт React-файлы по всем остальным путям и делает SPA fallback для маршрутов интерфейса.
3. Фронтенд и API работают на одном домене, поэтому CORS не становится отдельной зависимостью архитектуры.
4. Проверить обновление браузерной страницы на клиентском маршруте и один API-запрос после старта контейнеров.

### Шаг 3. Идентификация и права доступа

**Будущие файлы:**
- `backend/app/modules/identity/api.py`
- `backend/app/modules/identity/service.py`
- `backend/app/modules/identity/models.py`
- `backend/tests/modules/identity/test_authorization.py`

1. Утвердить матрицу ролей и статусов аккаунта по ТЗ.
2. Спроектировать выпуск и проверку сессии: cookie-сессия или bearer-токен. Решение принимается до реализации.
3. Проверка роли должна быть одной общей зависимостью FastAPI, а не копироваться в каждом маршруте.
4. Написать тесты для анонимного пользователя, блогера, модератора и администратора.

### Шаг 4. Транзакции и аудит

**Будущие файлы:**
- `backend/app/database/session.py`
- `backend/app/database/migrations/`
- `backend/app/modules/audit/service.py`
- `backend/tests/database/test_transaction_boundary.py`

1. Для каждой команды изменения данных использовать транзакцию PostgreSQL на время запроса.
2. Аудит пишется внутри той же транзакции.
3. До первого финансового endpoint определить правила блокировки строк и идемпотентности.
4. Написать тест: ошибка команды откатывает и бизнес-изменение, и запись аудита.

### Шаг 5. Обязательный контур воркеров

**Будущие файлы:**
- `backend/app/worker/celery_app.py`
- `backend/app/worker/tasks/`
- `backend/app/modules/outbox/`
- `docs/architecture/async-workflows.md`

1. Описать для каждой задачи: объём, допустимую задержку, правила повторов, последствия дублирования и способ контроля сотрудником.
2. Ввести outbox для надёжной передачи задач, появившихся после подтверждённой бизнес-транзакции.
3. Настроить Celery с Redis как брокером очереди.
4. Разделить задачи минимум на очереди `integrations`, `notifications`, `exports` и `scheduled`, только если различаются их нагрузка или права выполнения.
5. Celery Beat создаёт периодические задачи: сбор просмотров, уведомления о сроках, проверка неактивности.
6. Каждая задача должна быть идемпотентной: повторный запуск не создаёт повторное начисление, выплату или уведомление.

## Решения перед началом кода

1. Подтвердить модульный монолит как способ развёртывания.
2. Подтвердить единый домен: Nginx раздаёт React и проксирует `/api/v1`.
3. Подтвердить PostgreSQL как единственную основную БД.
4. Подтвердить React + TypeScript; альтернатива только одна: JavaScript с JSDoc-типами.
5. Подтвердить Celery + Redis как обязательную связку воркеров и очереди. RabbitMQ не входит в первый контур.

## Что намеренно не делаем в первой части

- OAuth и API соцсетей, кроме YouTube.
- Интеграцию с платёжным провайдером.
- Микросервисы, обмен HTTP между внутренними сервисами, event bus и Kubernetes.
- RabbitMQ и второй брокер очередей.
- Экранную часть сверх минимума, необходимого для проверки HTTP-контрактов.
