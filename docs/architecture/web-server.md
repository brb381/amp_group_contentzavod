# Веб-сервер: проектная спецификация

## 1. Назначение

Веб-сервер - это FastAPI-приложение, которое принимает HTTP-запросы от React-интерфейса, проверяет доступ, выполняет бизнес-команды в PostgreSQL и возвращает JSON. Он не выполняет долгие операции в рамках HTTP-запроса: отправку почты, YouTube-сбор, пакетные расчёты и выгрузки выполняют Celery-воркеры.

## 2. Граница ответственности

**Веб-сервер делает:**

- аутентификацию, авторизацию и управление сессиями;
- проверку формата входных данных;
- проверку бизнес-правил и допустимости статусов;
- транзакционные изменения PostgreSQL;
- запись аудита;
- создание записи в outbox для требуемой фоновой работы;
- выдачу версионированного JSON API.

**Веб-сервер не делает:**

- не хранит бизнес-данные в Redis;
- не запускает долгую работу внутри запроса;
- не обращается из браузерного кода напрямую к YouTube, SMTP или PostgreSQL;
- не содержит повторяющуюся бизнес-логику, перенесённую из модулей в маршруты API.

## 3. Сетевое взаимодействие

```text
Браузер
  -> HTTPS -> Nginx
      -> /              React static build
      -> /api/v1/*      FastAPI
      -> /health/live   FastAPI
      -> /health/ready  FastAPI

FastAPI
  -> PostgreSQL         основной источник данных и outbox

Celery Dispatcher / Worker / Beat
  -> Redis              очередь и расписание
  -> PostgreSQL         данные задачи, outbox, аудит
  -> YouTube / SMTP     внешние интеграции
```

React и API находятся на одном домене. Это исключает отдельную настройку CORS и делает cookie-сессии предсказуемыми.

## 4. Технологические решения сервера

| Зона | Решение | Причина |
| --- | --- | --- |
| HTTP | FastAPI | Валидация входных и выходных DTO через Pydantic, OpenAPI-документация, простой Python-код. |
| Работа с БД | SQLAlchemy 2 в синхронном режиме + psycopg | В запросах нет долгих I/O; синхронная модель проще в отладке. Внешние вызовы вынесены в воркеры. |
| Миграции | Alembic | Версионированная и воспроизводимая схема PostgreSQL. |
| Валидация | Pydantic | Один контракт для API и внутреннего use case. |
| Пароли | Argon2id | Современное хеширование паролей. |
| Фоновые задачи | Celery + Redis | Отдельные процессы для периодической и длительной работы. |

`async` в FastAPI не используется без конкретной необходимости. Его добавление не ускорит обычные операции PostgreSQL, но усложнит модель сессий и транзакций.

## 5. Структура кода

```text
backend/app/
  main.py                     запуск приложения и middleware
  api/
    v1/                       HTTP-маршруты и DTO API
  database/                   подключение, транзакции, миграции
  modules/
    identity/                 доступ, пароли, сессии, роли
    creators/                 профиль и социальные аккаунты
    catalog/                  товары и бренды
    content/                  ролики и публикации
    moderation/               решения и причины
    metrics/                  показания просмотров
    finance/                  расчёты, баланс, выплаты
    support/                  обращения и уведомления
    audit/                    журнал действий
    outbox/                   надёжная передача фоновых задач
  worker/                     конфигурация Celery и задачи
```

Внутри модуля допускаются только три прикладных слоя:

```text
api.py / schemas.py      HTTP-контракт
service.py               use case и бизнес-правило
models.py / repository.py данные PostgreSQL
```

Не вводим отдельные абстрактные фабрики, общий repository-base, CQRS-фреймворк или внутреннюю шину событий. Они не нужны при текущем масштабе.

## 6. Конвейер HTTP-запроса

### Чтение

```text
Nginx -> middleware request_id -> маршрут -> проверка сессии/роли
-> сервис модуля -> PostgreSQL -> DTO ответа -> JSON
```

### Изменение данных

```text
Nginx -> middleware request_id -> маршрут -> проверка сессии/роли
-> сервис модуля -> BEGIN
-> проверка бизнес-правил -> изменение данных + аудит + outbox
-> COMMIT -> JSON
```

Если транзакция не завершилась, не сохраняется ни бизнес-изменение, ни аудит, ни задача в outbox.

## 7. Формат API

Все рабочие endpoints имеют префикс `/api/v1`. URL содержит существительные, а действие передаётся HTTP-методом или отдельной командой, когда оно меняет состояние.

```text
GET    /api/v1/me
POST   /api/v1/auth/register
POST   /api/v1/auth/login
POST   /api/v1/auth/logout
POST   /api/v1/auth/password-reset-requests
POST   /api/v1/auth/password-resets
GET    /api/v1/creator-profile
PUT    /api/v1/creator-profile
POST   /api/v1/creator-profile/submission
```

Формат ошибки:

```json
{
  "code": "profile_not_approved",
  "message": "Профиль ещё не одобрен",
  "details": {},
  "request_id": "..."
}
```

Правила контракта:

- идентификаторы - UUID;
- дата и время - ISO 8601 в UTC;
- денежные суммы - целое число копеек, например `125050`, а не `1250.50` или `float`;
- перечисления статусов передаются строковыми значениями из утверждённого списка;
- список всегда содержит пагинацию: `items`, `page`, `page_size`, `total`;
- `request_id` добавляется в каждый ответ и лог.

## 8. Сессии и безопасность

### Выбранная модель сессии

Используются непрозрачные серверные сессии:

1. После успешного входа FastAPI создаёт случайный session ID.
2. В PostgreSQL хранится только хеш session ID, пользователь, время создания, время истечения, время последней активности и признак отзыва.
3. Браузер получает ID в cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, путь `/`.
4. При выходе, смене пароля или блокировке аккаунта сессия отзывается в PostgreSQL.

Это проще JWT: не требуются refresh-токены, ключи подписи и отдельная логика отзыва. Проверка сессии выполняется обычным запросом в PostgreSQL; на плановом масштабе это не создаёт узкого места.

### Защита запросов

- Пароль хранится только как Argon2id-хеш.
- Для cookie-авторизации мутационные запросы требуют CSRF-токен в заголовке.
- Вход, восстановление пароля и подтверждение email имеют rate limit через Redis.
- Nginx принимает только HTTPS и устанавливает базовые security headers.
- Проверка прав выполняется до вызова бизнес-сервиса.
- Значимые действия сотрудников, финансовые изменения и смены статусов пишутся в аудит с `request_id`, пользователем и IP.
- Сессия сотрудника автоматически истекает после периода бездействия; конкретное время задаётся конфигурацией и утверждается до реализации.

## 9. Транзакции и outbox

PostgreSQL является единственным источником состояния. Redis и Celery не хранят финансовый результат и не определяют статус бизнес-объекта.

Для команды, после которой нужна фоновая работа, сервер в одной транзакции:

1. Изменяет бизнес-данные.
2. Записывает аудит.
3. Добавляет строку `outbox_event` со статусом `pending`.
4. Подтверждает транзакцию.

Celery-задача-диспетчер читает подтверждённые события, ставит нужную задачу в очередь Redis и помечает событие отправленным. Повторный запуск диспетчера безопасен: у каждого события есть UUID и обработчик обязан быть идемпотентным.

Outbox обязателен для финансовых, модерационных и других значимых изменений. Для технического действия без последствий, например очистки кеша, допускается прямая постановка Celery-задачи.

## 10. Контракты API и воркеров

| Сценарий | Что фиксирует API | Что делает воркер |
| --- | --- | --- |
| Регистрация | пользователь, хеш пароля, согласия, токен подтверждения | отправляет письмо подтверждения |
| Сброс пароля | одноразовый токен | отправляет письмо восстановления |
| Новая публикация | карточка, URL, статус проверки | разбирает URL и получает YouTube-метаданные |
| Показания YouTube | задача сбора с внешним ID | получает viewCount, создаёт показание или запись ошибки |
| Выплата | запрос, блокировка суммы, аудит | отправляет уведомление менеджеру |
| Excel-выгрузка | запрос на выгрузку | создаёт файл и уведомляет автора |
| Закрытие периода | запись запуска расчёта | рассчитывает начисления идемпотентно |

## 11. Логирование и диагностика

- `request_id` создаётся на входе в Nginx или FastAPI и передаётся до воркера через outbox.
- Логи пишутся структурированным JSON без паролей, токенов, реквизитов и полного содержимого чувствительных полей.
- `/health/live` отвечает, что процесс FastAPI запущен.
- `/health/ready` дополнительно проверяет соединение с PostgreSQL. Redis не должен делать пользовательский API недоступным, если временно не работает очередь.
- Ошибки воркеров видны в журнале задач и в административной очереди ошибок, но не скрывают уже подтверждённые данные БД.

## 12. Решения, требующие утверждения до реализации

1. Максимальное время неактивности сессии сотрудника.
2. Время жизни сессии блогера и правило её продления.
3. Какие действия кроме перечисленных в ТЗ считаются значимыми для аудита.
4. Нужна ли двухфакторная аутентификация сотрудникам при первом запуске или это следующий этап.
5. Политика хранения готовых Excel-файлов и место их хранения.

## 13. Первый реализуемый вертикальный срез

Первый кодовый срез не должен начинаться с полной доменной модели. Он должен проверить весь контур веб-сервера:

1. `GET /health/live` и `GET /health/ready`.
2. Контейнеры Nginx, FastAPI, PostgreSQL, Redis, Celery Worker и Celery Beat.
3. Миграция таблиц пользователя, сессии, согласия, аудита и outbox.
4. Регистрация блогера с принятием согласий.
5. Постановка и выполнение фонового письма подтверждения.
6. Вход, выход и получение `GET /api/v1/me`.

Этот срез подтвердит маршрутизацию, БД, сессии, транзакции, аудит, outbox, Redis и Celery до начала модулей публикаций, расчётов и выплат.
